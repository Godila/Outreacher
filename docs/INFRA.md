# Инфраструктура: VM и DNS под аутрич-сервис

**Дата:** 2026-09-23 · привязано к решениям дискавери (§4 DISCOVERY.md): отправка — сабдомен на собственном MTA заказчика (§1.1, обновлено после ответа Beget) + свой бэкенд на Beget VM.

Домен в примерах: `brend.ru` (замените на свой). IP: `<MTA_IP>` — VM почтового сервера, `<APP_IP>` — VM бэкенда.

---

## 1. Хостер: Beget (решено) — что заказать и что запросить

Домены, DNS-зона, VPS и IP — в одном аккаунте Beget. ДЦ в РФ → ФЗ-152 (хранение ПДн) соблюдён.

**Заказать:** 2 VPS по конфигурациям §2 (ОС Ubuntu 24.04). Выделенный IPv4 входит в каждый VPS.

**Один тикет в поддержку (после создания VM-MTA) — только PTR:**

Ответ поддержки Beget (24.09.2026): **порты на VPS не блокируются** (25-й открыт по умолчанию — тикет не нужен); собственный почтовый сервер на VPS разрешён, отправка/приём «не регламентируются»; IP меняется самостоятельно в «Настройках сети» (делистинг при понижении репутации — на своих плечах); SMTP-релей своей почтовой системы не предоставляется (нам и не нужен). Для PTR нужны: выделенный IP (у VPS свой), оплаченный аккаунт от месяца. В тикете указать: IP, значение `mta-news.adel-factory.ru`, назначение — обратная запись для собственного почтового сервера (Postfix, информационные письма своей клиентской базе).

**После выдачи IP:** проверить по блэклистам — [Spamhaus](https://www.spamhaus.org), [Barracuda](https://barracudacentral.org/lookups), [MXToolbox](https://mxtoolbox.com/blacklists.aspx). Грязный IP — сразу просить замену.

**В панели Beget:**
- DNS-зону домена вести в их панели (все записи §4.1), TTL 3600.
- Брандмауэр панели Beget продублировать ufw/iptables на хосте (два слоя: сетевой + хостовый).
- Снапшоты VPS — бэкап конфигурации MTA (Maildir не критичен: сервис переносит ответы в свою БД).

**Чего не делать:** не отправлять кампании через `smtp.beget.com` (SMTP шаред-хостинга) — там лимиты тарифа, общий пул репутации и их ToS о рассылках; наш канал — собственный MTA на VPS.

### landvps.ru — не для продакшена этого проекта

Второй аккаунт (landvps) рассмотрен и отклонён для прода. Причины — по отзывам ([Hosting101](https://hosting101.ru/landvps.ru): ~29% жалоб на «протухшие» IP; [Отзовик](https://otzovik.com/review_18468560.html): молчаливая смена IP, удаление сервера через день после неуплаты; [Т-Банк Отзывы](https://www.tbank.ru/reviews/company/landvps/210020): недоступность GitHub/Docker Hub с сервера):

- **Грязные/«протухшие» IP** — дисквалификатор для MTA: почтовая репутация строится на IP, блэклист-наследие не отмыть.
- **Молчаливая смена IP** — катастрофа для MTA (PTR + прогрев привязаны к IP) и неприятность для APP (перевыпуск DNS/сертификатов).
- **Недоступность GitHub/Docker Hub** — ломает деплой-канон (git pull + docker build/pull).
- Быстрое удаление при просрочке — риск потери прод-данных.

Допустимое применение: staging/тестовые машины, одноразовые окружения — где потеря IP или сервера не стоит ничего.

## 1.1. ~~Ускоренный старт: почта Beget~~ — ЗАКРЫТО поддержкой Beget (23.09.2026)

Ответ поддержки: **почтовые ящики на сабдомене создать нельзя** (только основной домен). Ящики на основном домене нам не подходят: его MX указывает на собственный сервер заказчика — ответы до Beget-ящиков не дошли бы, плюс терялась изоляция репутации.

Лимиты Beget-почты для справки (если основной домен когда-нибудь переедет на Beget): SMTP — 30 писем/мин, **1500 писем/час**; mail() — 30/мин; письмо ≤75 МБ (SMTP); ≤300 получателей на письмо; запрещены ящики на доменах tk/ga/ml/qq/cf. Для наших объёмов (50–100/день) лимиты избыточны — проблема была только в сабдомене.

**Действующий план — сабдомен на собственном почтовом сервере** (вариант B из дискавери, дёшево):
- Корпоративный MTA уже поднят → добавляем на него почтовый домен `news.<домен>` и 2 ящика. Отдельная VM-MTA не нужна, пока не упрёмся.
- DNS по §4.1 без изменений: MX `news.<домен>` → hostname вашего MTA, SPF `v=spf1 ip4:<IP вашего MTA> -all`, DKIM 2048 (новый селектор `mail-news._domainkey.news.<домен>`), DMARC на сабдомене и корне.
- Преимущество против Beget-shared: выделенный «возрастной» IP с уже наработанной репутацией (не общий пул), свои лимиты.
- Код сервиса не меняется: пул отправителей абстрактен (`senders` — SMTP/IMAP любые).

**Триггеры отдельной VM-MTA:** лимиты/нагрузка на корпоративный сервер · доставляемость деградирует · вход в cold-фазу.

## 2. Целевая схема: две VM (VM-APP — сразу, VM-MTA — по триггерам §1.1)

Разделение причин: репутация почтового IP хрупкая, а веб-приложение (публичные вебхуки Б24, UI) — поверхность атаки; компрометация приложения не должна касаться MTA. И наоборот: веб-трафик и API-вызовы не должны жить на почтовом IP.

### VM-MTA — кампейн-почтовый сервер

| Параметр | Значение |
|---|---|
| CPU / RAM | **2 vCPU / 4 GB** (Postfix + Dovecot + OpenDKIM + Rspamd — с запасом при наших 50–100 письмах/день) |
| Диск | 40 GB NVMe (Maildir ответов живёт до забора сервисом; чистится) |
| Сеть | 1 выделенный IPv4, PTR → `mta-news.brend.ru` |
| ОС | Ubuntu 24.04 LTS |
| Стек | **docker-mailserver** (Postfix, Dovecot IMAP, OpenDKIM, Rspamd, fail2ban) одним compose |

Почему docker-mailserver, а не Mailcow: Mailcow — тяжёлый (просит ~6 GB RAM, полный веб-интерфейс, MySQL, ClamAV), его админка избыточна для 2–5 ящиков; docker-mailserver лёгкий, декларативный (конфиги в git), лёгок в бэкапе. Альтернатива «руками Postfix» — не стоит: docker-mailserver закрывает best practices из коробки.

Ящики на старте: 2 шт. (например `anna@`, `sergey@`) — имена реальных «отправителей» кампаний.

**Firewall VM-MTA (минимальная поверхность):**

| Порт | Доступ | Назначение |
|---|---|---|
| 25/tcp | мир (вход) + исходящий | приём ответов/bounce, отправка |
| 587/tcp | только `<APP_IP>` | submission (бэкенд шлёт письма с аутентификацией) |
| 993/tcp | только `<APP_IP>` | IMAPS (бэкенд слушает ответы) |
| 22/tcp | только ваш IP / VPN | SSH, ключи, без паролей |

### VM-APP — бэкенд сервиса

| Параметр | Значение |
|---|---|
| CPU / RAM | **2 vCPU / 4 GB** (nginx + FastAPI web + worker + Postgres — с запасом; сотни контактов, один оператор) |
| Диск | 40 GB NVMe |
| Сеть | IPv4 (выделенный проще для вебхуков Б24 и TLS) |
| ОС | Ubuntu 24.04 LTS |
| Стек | docker compose по канону проекта: nginx (TLS, Let's Encrypt) → web (FastAPI) + worker (планировщик секвенций, отправитель, IMAP-листенер) + postgres |

Порты наружу: 80/443 (nginx: UI, API, вебхуки Б24, эндпоинт отписки RFC 8058), SSH — ключи/ограничение по IP.

Бэкап: cron `pg_dump | gzip` ежедневно + проверка `gzip -t` (канон), Maildir на MTA — опционально раз в неделю (сервис копирует ответы в свою БД, письма на MTA — расходник).

## 3. Вариант B (бюджетный): одна VM

4 vCPU / 8 GB / 80 GB, всё в одном compose (mta + app). Экономия ~800–1200 ₽/мес. Цена: общий IP у почты и веб-приложения (см. риски выше), один firewall на всё. При наших объёмах допустимо, но при росте в cold-фазы всё равно разъезжается на две.

## 4. Сабдомены и DNS

### 4.1 Карта записей

Отправляющий домен кампаний — **выделенный сабдомен** (изоляция репутации от корпоративной почты). Варианты имени: `news.brend.ru`, `info.brend.ru`, `hello.brend.ru` — получатель видит его в From (`Анна <anna@news.brend.ru>`). **Не используйте `mail.`** — он почти наверняка занят hostname/MX корпоративной почты.

Пример ниже для `news.brend.ru` и hostname MTA `mta-news.brend.ru`:

| Запись | Тип | Значение | Зачем |
|---|---|---|---|
| `mta-news.brend.ru` | A | `<MTA_IP>` | hostname почтового сервера: HELO/EHLO, TLS-сертификат |
| PTR для `<MTA_IP>` | rDNS (через хостера) | `mta-news.brend.ru` | обязательна: 25% антиспам-проверок начинаются с PTR |
| `news.brend.ru` | MX 10 → `mta-news.brend.ru` | | приём ответов и bounce на адреса From |
| `news.brend.ru` | TXT (SPF) | `v=spf1 ip4:<MTA_IP> -all` | только наш сервер, строгий `-all` |
| `mail-news._domainkey.news.brend.ru` | TXT (DKIM) | генерируется OpenDKIM (2048-bit) | селектор `mail-news`; публикуется после настройки MTA |
| `_dmarc.news.brend.ru` | TXT (DMARC) | `v=DMARC1; p=none; rua=mailto:dmarc@brend.ru; adkim=s; aspf=s` | старт soft, `rua` собирает отчёты; через 1–2 мес ужесточаем до `quarantine` |
| `_dmarc.brend.ru` (корень) | TXT | `v=DMARC1; p=none; rua=mailto:dmarc@brend.ru` | гигиена корневого домена |
| `outreach.brend.ru` | A | `<APP_IP>` | UI/API сервиса, вебхуки Б24, `https://outreach.brend.ru/unsub/<token>` — one-click отписка (RFC 8058) |

### 4.2 Чего НЕ выпускаем (намеренно)

- **Трекинг-домен/редиректор** — нет пикселей и кликовых редиректов по дизайну (доставляемость); трафик меряем UTM-метками напрямую на ваши лендинги.
- **Lookalike-домены** (`brend-mail.ru` и пр.) — cold-трюк фазы 2, и только если холодный аутрич подтвердится; для своих клиентов вредит доверию.
- **MTA-STS/TLS-RPT** — опциональная гигиена приёма, отложена (важно для получателей, не для нашей отправки).

## 5. Порядок запуска (чек-лист)

**Почтовый путь (актуально, §1.1):** сабдомен `news.<домен>` добавляется на ваш собственный почтовый сервер — MX/SPF/DKIM/DMARC по §4.1 указывают на ваш MTA; шаги 1 и 3 ниже (Beget-тикет на 25-й порт и docker-mailserver) не нужны, пока письма идут через корпоративный сервер.

1. Купить VM по критериям §1; проверить IP по блэклистам; поставить PTR.
2. Выпустить DNS §4.1 (кроме DKIM — после генерации ключа).
3. Поднять docker-mailserver на VM-MTA: домен `news.brend.ru`, ящики, DKIM-ключ 2048 → опубликовать TXT.
4. TLS: Let's Encrypt на `mta-news.brend.ru` (SMTP STARTTLS) и на `outreach.brend.ru` (HTTPS).
5. Проверка: отправить тесты на mail-tester.com — цель **10/10** (SPF pass, DKIM pass, DMARC pass, PTR ok); seed-проверка на ящики Mail.ru/Яндекс/Gmail — инбокс.
6. Зарегистрировать `news.brend.ru` в постмастере Mail.ru (FBL, заголовок `Feedback-ID`, `X-Postmaster-Msgtype`) и в постмастере Яндекса.
7. Поднять каркас APP-VM (compose, nginx, health) — под бэкенд.
8. Прогрев объёмов — после подключения бэкенда: 5 → 10 → 20 → 30–50/день на ящик за 1–2 недели, старт с лояльного сегмента.

## 6. Фазовые закладные (не сейчас)

- Второй сабдомен (например `promo2.brend.ru`) — при росте тёплой базы ×5.
- Cold-РФ (фаза 2): пулы ящиков у провайдеров (Яндекс 360/VK) на вторичных доменах — в общем пуле отправителей сервиса рядом со своим MTA (§4 DISCOVERY, «ловушка»).
