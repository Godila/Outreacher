## 1. Главный вывод дискавери: это lifecycle-маркетинг, а не cold outreach

Практически вся публичная методология email-аутрича (Instantly, Lemlist, Woodpecker, Belkins, Backlinko) описывает **холодные** письма незнакомым людям. Наш случай принципиально другой — **коммуникация с собственной клиентской базой**, и это меняет почти все правила:

| Аспект | Cold outreach (бенчмарки из исследований) | Наш кейс (свои клиенты) |
|---|---|---|
| Юридика (РФ) | Реклама без согласия — штраф до 1 млн ₽ за факт (ч. 4.1 ст. 14.3 КоАП) | Письма своим клиентам о **своих** товарах/услугах — вне понятия рекламы (п. 4–7 ч. 2 ст. 2 ФЗ-38). Провокация — только чужие офферы в письмах |
| Ожидаемый reply rate | 3,4–5,1% (падает год к году) | Выше в разы: получатель знает бренд. Ориентир для реактивации — **8–15%**, планка «плохо» выше, чем у cold |
| Доставляемость | Пулы прогретых сабдоменов, ротация ящиков, warmup-сети | Достаточно **одного выделенного сабдомена и 1–2 ящиков** — объёмы малы, получатели лояльны, жалобы маловероятны |
| Персонализация | Внешние сигналы (фандрынг, найм, техстек) | **Внутренние данные CRM**: история покупок, давность, суммы, категории — у нас уже есть всё |
| Секвенции | 4–7 касаний | **2–4 касания** — отношения есть, длинные цепочки раздражают своего клиента |
| Warmup | 2–8 недель по графику | Мягкий прогрев 1–2 недели до 30–50 писем/день — и всё |

**Следствие для сервиса:** мы строим не «клона Instantly», а **конструктор клиентских кампаний поверх CRM**: сегментация из Б24 → секвенции с автостопом на ответ → маршрутизация диалогов обратно менеджерам в Б24. Специфичный для cold функционал (пул доменов, ротация, warmup) в фазе 1 не строим, но закладываем архитектурно — холодный аутрич заявлен как фаза 2 (§6.1).

## 2. Методологическая рамка (playbook)

### 2.1 Сегментация — главный рычаг результата

Исследования однозначны: сегментированные/триггерные кампании дают **3–5x больше встреч**, чем bulk (FormanNorden), а малые кампании (<50 контактов) получают reply **5,8%** против **2,1%** у кампаний 500+ (Belkins, 16,5 млн писем). Для своей базы сегментация = **RFM по данным сделок Б24**:

- **Recency** — давность последней сделки/активности (ядро реактивации: «спящие 6/12/24 мес»);
- **Frequency/Monetary** — число и сумма покупок (допродажи: «покупали X — предложить Y»);
- **Категория товара** — что именно покупали (релевантный оффер);
- **Статус в CRM** — активная сделка в работе → исключить из автоматических кампаний;
- **Вовлечённость** — отвечал ли на прошлые кампании, открывал/кликал (не выжигать базу повторными кампаниями неответившим).

Сегменты собираются запросами `crm.contact.list` / `crm.deal.list` по фильтрам (или смарт-процессами/сегментами CRM-маркетинга Б24, если уже настроены).

### 2.2 Четыре типа кампаний → паттерны секвенций

Общие правила секвенций (из данных Backlinko 12 млн, Woodpecker 20+ млн, Instantly):
- **42–58% всех ответов приносят follow-up'ы** — кампания из одного письма теряет половину результата; но после ~4 follow-up жалобы утраиваются — для своей базы стоп на 2–4 касаниях.
- Первый follow-up — **пик эффективности** (8,4% reply у Belkins), дальше отдача падает.
- Интервалы: первый follow-up через **2–3 рабочих дня**, далее ~неделя; нарастание 2→4→7.
- Follow-up — **reply'ем в тот же тред** (сохраняет контекст, выглядит как диалог, ниже спам-скор).
- Окно отправки: **вт–чт, 6–9 утра по локали получателя** (Мск для РФ/СНГ), вторичное 13–15.
- **Bump должен добавлять ценность** («just checking in» снижает встречи на 14% — Gong/Woodpecker): новый аргумент, кейс, другой угол — не «ну что, надумали?».

| Тип кампании | Секвенция | Специфика |
|---|---|---|
| **Реактивация молчаливых** | 3–4 шага: письмо → +2–3 дня bump → +7 дней «последнее письмо» с оффером возврата | Тон «мы помним вас», персонализация последней покупки; финальный шаг — явный оффер/скидка |
| **Анонс продукта** | 1 broadcast + 1–2 напоминания **только не откликнувшимся** | Допустим лёгкий HTML (это newsletter-класс), UTM-ссылки на лендинг; метрика — клики и заявки |
| **Допродажи** | 2–3 шага, сильно персонально | Опирается на историю покупок («вы брали X — к нему Y»); интерес-CTA, не хард-селл |
| **Контент/опросы** | 1 broadcast (+1 напоминание) | Без продажи; NPS-опрос — отдельная механика со ссылкой на форму |

**Stop-правила (автостоп секвенции) — обязательны для всех типов:** любой человеческий ответ · отписка · появление активной сделки у контакта (его подхватил менеджер). OOO-автоответ — **не стоп**: пауза с возобновлением через 1–2 рабочих дня после даты возврата (ловушка: многие инструменты продолжают слать во время отпуска — HubSpot Community).

### 2.3 Копирайтинг: что подтверждено данными

| Элемент | Практика | Данные |
|---|---|---|
| Длина письма | **50–125 слов** (лучший диапазон) | 8,2% reply против 3,9% у 200–300 слов (Overloop, 3 млн писем) |
| Тема | **36–50 символов**, персонализированная, без кликбейта | +30,5% ответов за персонализацию (Backlinko); гиммики: +30% opens, **−12% replies** (30MPC/Gong) |
| Структура | Problem-led язык клиента, не ROI-язык | 132 552 письма Gong: «увеличим вашу отдачу на X%» в первом касании не работает |
| CTA | **Один interest-based вопрос** («Интересно?», «Актуально?») | 304 174 письма Gong: interest-CTA 12% ответов против 7% у «есть 15 минут во вторник?» |
| Формат | Plain text (или минимальный HTML), ≤1 ссылка HTTPS, без вложений | HTML бьётся bounce на 674% чаще (Hunter); +15–25% ответов у plain text |
| Подпись | Ссылка на сайт/профиль в подписи допустима и полезна | +9,8–11,5% ответов (Backlinko) |
| Футер | Идентификация юрлица + отписка | Требование правил Mail.ru (неэлектронные контакты в каждом письме) и ФЗ-38 |

Фреймворки (PAS / BAB / AIDA) — практика без жёстких A/B-доказательств; для реактивации лучше всего работает «напоминание о контексте → ценность → мягкий вопрос».

### 2.4 Персонализация из CRM (наш козырь)

Данные: персонализация выше имени/компании даёт **17–18% reply против 7–9%** базовой (Woodpecker); продвинутая персонализация — до 5x ответов. В cold для этого ищут внешние сигналы; **у нас сигналы уже лежат в Б24**:

- что и когда покупали (товар, дата, сумма);
- давность и частота (RFM-сегмент);
- ответственный менеджер (письмо «от» него, reply приходит ему);
- история общения (был ли недоволен, был ли NPS-ответ).

Merge-шаблоны вида `{{contact.name}}, {{last_deal.product}}, {{last_deal.months_ago}} мес назад`. AI-генерация строк — опционально и **под контролем человека**: генерик-AI письма дрябнут (reply агентств упал с 6,8% до 5,8% за год), AI при человек-контроле паритетен с людьми (9,8% vs 10,2%).

### 2.5 Обработка ответов: классификация и маршрутизация в Б24

Каждый входящий ответ классифицируется (5 категорий — отраслевой стандарт Instantly/Allston):

| Категория | Действие сервиса | Действие в Б24 |
|---|---|---|
| **Positive** (интерес, вопрос) | Стоп секвенции, немедленное уведомление | Комментарий в таймлайн + дело «Связаться» ответственному менеджеру |
| **Negative** (отказ) | Стоп секвенции, контакт в cooldown | Комментарий в таймлайн, тег «отказ» |
| **OOO / автоответ** | Парсинг даты возврата → пауза → resume через 1–2 раб. дня | — |
| **Отписка** | Мгновенный глобальный стоп-лист (навсегда, ст. 18 ФЗ-38) | Пометка контакта «не рассылать» |
| **Referral** («спросите Иванова») | Стоп секвенции | Комментарий в таймлайн |

Ответственный менеджер получает ответ в свой ящик напрямую (reply-to реального ящика) + дублирующее уведомление в Б24 — диалог продолжает человек, автоматизация только ведёт до первого ответа.

### 2.6 Гигиена базы и частотные лимиты

- **Распад базы ~22,5%/год** → верификация email перед каждой кампанией и реверификация каждые 3–6 мес (hard bounce цель <2%, стоп кампании при >3–4%).
- **Hard bounce** → suppression немедленно; soft → 1–2 ретрая → suppression.
- **Cooldown между кампаниями: 2–3 месяца** на контакт, и только с новым оффером; ответившим негативно — дольше.
- **Суточный потолок: 20–50 писем на ящик** — при наших объёмах (сотни контактов × 2–4 шага ≈ 70–100 писем/день в пике) достаточно 2 ящиков.
- **Исключать контакты с активными сделками** — им персональные письма менеджера, не автоматические цепочки.

## 3. Метрики успеха

Open rate — метрика-фантом (Apple MPP завышает на ~49%): показываем справочно, решения по нему не принимаем.

| Метрика | Цель | Комментарий |
|---|---|---|
| Delivery rate | ≥98% | Ниже — стоп и разбор DNS/репутации |
| Hard bounce | <2% | Стоп кампании при >3–4% |
| Reply rate | >8% (реактивация) | Cold-бенчмарк 3,4–5,1% — для своей базы это «плохо» |
| Positive reply rate | ~40% ответов | Классификация ответов обязательна |
| Отписки/жалобы | <0,1–0,3% | FBL Mail.ru/Яндекс + постмастеры |
| Клик по UTM | по типу кампании | Главный сигнал для анонсов/конdtnt |
| Ожившие сделки | конверсия кампании → сделки в Б24 | Финальная метрика; связка кампания→сделка через UTM/source |

A/B-тесты: один элемент за раз (тема → CTA → первая строка), ≥1000 на вариант для значимости — при сотнях контактов честный A/B невозможен, поэтому **на старте A/B не строим**, копим данные.

## 4. Инфраструктура отправки: варианты и критерий выбора

Объёмы фазы 1: кампания на 500 контактов × 3 шага ≈ **70–100 писем/день в пике** — на порядок ниже порогов bulk-отправителей (5000/день). Главный вопрос не объём, а **надёжность попадания в инбоксы Mail.ru и Яндекса**, где живёт большинство получателей РФ. Жёсткая реалия с 29.06.2026: бесплатный IMAP/SMTP у Яндекса и VK закрыт — либо бизнес-тариф, либо свой сервер.

### Вариант A. Бизнес-почта провайдера на своём домене (Яндекс 360 / VK для бизнеса)

Свой домен + 1–2 ящика на выделенном сабдомене у провайдера; отправка/приём по SMTP/IMAP бизнес-тарифа (~200–400 ₽/ящик/мес).

- **Плюсы:** наследуем репутацию IP-пулов провайдера — ключевой фактор попадания в инбоксы Mail.ru/Яндекса с первого дня; постмастеры и FBL — в пару кликов; DKIM/SPF/DMARC без операционки; ящики заведены за час.
- **Минусы:** тарифные лимиты (Яндекс 500/24ч — наш потолок 50/ящик втрое ниже); ToS-серая зона для «рассылок»: наш профиль — 1-to-1 персонализированные письма, выглядящие как обычная деловая переписка, но актуальную оферту тарифа стоит проверить; зависимость от политик провайдера.
- **ПДн:** контакты хранятся в нашем сервисе и Б24; SMTP — только транспорт, база провайдеру не передаётся.

### Вариант B. Собственный почтовый сервер (self-hosted SMTP)

Postfix + OpenDKIM + DMARC + Dovecot (IMAP для приёма ответов) на VPS с выделенным IP.

- **Плюсы:** полный контроль; стоимость не растёт с числом ящиков; нет ToS-ограничений провайдера; ПДн полностью на своей инфраструктуре (максимально чистый ФЗ-152-сюжет); неограниченные ящики/алиасы; навыки и VM-инфраструктура у команды уже есть.
- **Минусы (серьёзные):** свежий IP с VPS для Mail.ru/Яндекса — самый подозрительный класс отправителей: разгон репутации 2–6 недель, первые недели — «Спам»; нужен хостер с открытым 25-м портом и делегированием rDNS; стек надо обслуживать (очередь, DKIM-ротация, блэклисты, TLS-сертификаты); приём ответов — свой Dovecot.
- **Условия жизнеспособности:** чистый выделенный IP (проверка по Spamhaus/Barracuda/SORBS до покупки), rDNS → `mail.домен`, регистрация домена в постмастерах Mail.ru/Яндекс + FBL `Feedback-ID`, плавный набор объёма от ~20/день.

### Почему «свой сервер как фундамент будущего cold» — ловушка

Инстинкт «поднять свой сервер и масштабировать аутрич» контрпродуктивен: cold по РФ надёжнее идёт **ящиками провайдера на вторичных доменах** (наследованная репутация пулов), cold на международку — **Gmail/M365-ящиками**. Мелкий отправитель со своего IP — самый дискриминируемый класс у всех фильтров; собственный SMTP с ротацией доменов — западный паттерн для больших объёмов, который в РФ работает плохо. Следствия:

- Собственный сервер — это оптимизация **стоимости/контроля/независимости для фазы 1** (тёплая база), а не фундамент cold.
- Фундамент cold — **архитектура пула отправителей** (§6.1): много ящиков у любых провайдеров, ротация, прогрев, вторичные домены. 

### Решение (зафиксировано с заказчиком): вариант B — собственный сервер

Почтовый сервер уже поднят — отправляем с него: репутация нарабатывалась вместе с корпоративной почтой, ограничений ToS нет, ящики бесплатны, операционка знакома команде. Чек-лист готовности к кампаниям:

1. **Выделенный сабдомен** для кампаний (например `go.бренд.ru`): ящики и DNS кампаний — на нём, изоляция репутации от основной корпоративной почты. Объём набирать плавно (5 → 30–50/день на ящик за 1–2 недели), начиная с самых лояльных сегментов (недавние клиенты).
2. **DNS сабдомена**: SPF (только свой сервер, без лишних include) → DKIM 2048 (OpenDKIM) → DMARC `p=none; rua=...`.
3. **Постмастеры**: регистрация сабдомена в постмастере Mail.ru (FBL с заголовком `Feedback-ID` + `X-Mailru-Msgtype`) и в постмастере Яндекса (DKIM для массовых отправок у него обязателен). Жалующихся через FBL — автоматически в отписку.
4. **Аудит IP перед стартом**: проверка по Spamhaus/Barracuda/SORBS (у возрастного сервера обычно чисто, но проверить), rDNS → hostname сервера, исходящий 25-й порт открыт.
5. **Приём ответов**: тот же сервер (IMAP); сервис слушает ящики кампаний через IMAP IDLE.
6. **Отписка**: заголовки RFC 8058 (one-click) + заметная ссылка в футере (правила Mail.ru — доступна ≥30 дней; ФЗ-38 — обработка мгновенная и навсегда).
7. **Запас масштабирования тёплой фазы**: рост базы ×5 = добавить ящики на сабдомене (бесплатно, свой сервер), дальше — второй сабдомен. Выделенный IP не нужен (<50k/мес).

Слой отправителей в сервисе остаётся **абстракцией** (свой сервер + любые провайдерские SMTP в одном пуле) — это же окно в cold-фазу: пулы для cold по РФ собираются ящиками провайдеров на вторичных доменах (см. «ловушку» выше), а не нагрузкой на свой сервер.

## 5. Юридический контур (чек-лист РФ)

1. **Ядро — фиксация согласий в Б24**: у каждого контакта храним источник и дату получения email (из сделки, с сайта, оффлайн). Презумпция отсутствия согласия — на отправителе; письма своим клиентам о своих услугах вне ФЗ-38, но доказательство «свой клиент» = история сделок в CRM.
2. **Мгновенная отписка навсегда** (ст. 18 ФЗ-38) + глобальный suppression list: отписавшиеся, жаловавшиеся (FBL), hard bounce.
3. **Без чужих офферов** в письмах (иначе — реклама со всеми требованиями согласия; пометка «Реклама» — страховочная опция в футере).
4. **ФЗ-152**: сервис — оператор ПДн → уведомление РКН до старта (pd.rkn.gov.ru), политика обработки, **хранение ПДн в РФ** (наш собственный сервис на VM в РФ соответствует; выгрузка базы в зарубежный SaaS — риск локализации).
5. **Маркировка erid/ОРД на email-рассылки не распространяется** (письма РКН 24.10.2023 + позиция ФАС; подтверждено после изменений 01.09.2025) — но это ведомственные позиции, не норма закона: мониторим разъяснения, в футере пометка «Реклама» для писем с чужими офферами.
6. **Футер каждого письма**: идентификация юрлица + неэлектронные контакты (правила Mail.ru) + заметная отписка.

## 6. Функциональные требования к сервису (из методологии)

Требования выведены напрямую из playbook — каждое обосновано находками выше:

**MVP (ядро ценности):**
1. **Синхронизация базы** из Б24 (контакты + сделки: RFM-поля) — выборка по фильтрам/сегментам.
2. **Сегмент-конструктор**: сохранённые сегменты (фильтры по давности/суммам/категориям/статусу), исключение активных сделок и стоп-листа.
3. **Кампании и секвенции**: шаблон = шаги (email + задержка), merge-теги из CRM, окна отправки (рабочие дни, часы Мск), лимит писем/день.
4. **Отправка** через SMTP 1–2 ящиков с сабдомена, тредовые follow-up (In-Reply-To), UTM-ссылки, футер с отпиской, заголовки RFC 8058 + Feedback-ID.
5. **Инбокс-листенер** (IMAP IDLE): детект ответов, классификация (positive/negative/OOO/отписка/referral — правила + LLM), автостоп секвенций, OOO-пауза с resume.
6. **Маршрутизация в Б24**: отправка — email-активность в таймлайн; ответ — комментарий + дело менеджеру; отписка/bounce — пометка контакта.
7. **Стоп-лист** (suppression): отписки, FBL-жалобы, hard bounce — глобальный, навсегда.
8. **Метрики по кампании/шагу**: delivery, bounce, reply, positive reply, отписки; UTM-клики через связь с Б24 (источник сделки).

**Виток 2 (после первого боевого цикла):**
9. A/B-варианты шага (когда наберётся объём), cooldown-контроль между кампаниями, верификация email (API-верификатор), календарь кампаний, AI-черновики персональных строк под контролем оператора.
10. Робот Б24 «добавить в кампанию» (bizproc.robot.add) — запуск секвенции прямо из воронки.

**Закладные под cold-аутрич (фаза 2) — проектируем сейчас, реализуем по мере надобности:**
11. **Пул отправителей** — первоклассная сущность: sender-аккаунты с типом транспорта (SMTP провайдера / свой сервер / API), дневными лимитами и health-статусом. Фаза 1 работает с пулом из 1–2 ящиков; фаза 2 расширяет пул без изменения кода.
12. **Ротация кампания→пул** с учётом лимитов + лимит на домен получателя (не слать >N писем/день в одну компанию-получателя — признак спама).
13. **Домены-сущности**: DNS-валидация (SPF/DKIM/DMARC-чекер), статус прогрева и репутации — для вторичных доменов cold-фазы.
14. **Warmup-хук**: тип фоновой задачи «прогрев» (внутрипуловые касания между своими ящиками) — включается при пуле >1; для Gmail-пулов учитывать запреты Google на warmup-сети (окт. 2025).
15. **Интерфейс верификатора email** (обязательная проверка перед cold-кампанией; для тёплой базы — опция).
16. **Типы шагов секвенции расширяемы**: email сейчас; linkedin/звонок — заглушки на будущее.
17. **Юридический слой кампании и реестр согласий** (cold заявлен на рынок РФ): тип письма (информационное/рекламное), поля согласия у контакта (источник, дата, текст, IP) — фундамент легального cold. Cold по РФ без согласий = риск 300 тыс.–1 млн ₽ за каждый факт (ч. 4.1 ст. 14.3 КоАП), поэтому в виток 2 закладываем **механизмы заблаговременного сбора согласий**: формы на сайте/лендингах (лид-магниты), фиксация согласий в Б24 при каждом касании — база согласий копится уже с фазы 1, пока идут тёплые кампании.
18. **Пулы cold-РФ**: вторичные домены + ящики провайдеров (Яндекс 360/VK для бизнеса) в общем пуле отправителей рядом со своим сервером. Свой сервер — тёплые кампании и транзакционные письма; провайдерские пулы — холодные (наследованная репутация, см. §4 «ловушка»).

**Не строим в фазе 1 (обоснованно):** spintax, LinkedIn-канал, открытый трекинг-пиксель, мультиязычность, мультиарендность. Пул отправителей, домены, warmup, верификация, реестр согласий — проектируются как сущности сейчас (п. 11–18), реализуются по мере входа в cold.

## 7. Что дальше

После утверждения дискавери — 2–3 варианта архитектуры сервиса с трейд-оффами (предварительный расклад: собственный сервис рядом с Б24 — рекомендую; готовый SaaS + glue — дисквалифицирован юридикой ПДн и отсутствием нативной интеграции; штатный CRM-маркетинг Б24 — только как дешёвая параллель для broadcast-анонсов) → проектирование → спецификация → план реализации.
